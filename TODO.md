## 🏗️ Recommended Design Patterns

### Primary: **Adapter + Strategy + Repository + Observer**

| Pattern | Where Used | Why |
|---|---|---|
| **Adapter** | Each supplier connector | Normalizes different supplier response shapes into one `FlightDTO` |
| **Strategy** | Supplier polling scheduler | Each supplier has its own polling interval strategy, configurable via DB/config |
| **Repository** | Flight data access | Decouples Eloquent from business logic; swappable data source |
| **Observer / Event-Listener** | Flight updates | Fires `FlightUpdated` event when a supplier returns new data; cache invalidation |
| **DTO (Data Transfer Object)** | Supplier → App boundary | `FlightDTO` is the single contract all adapters must produce |
| **Command Bus (Laravel Jobs)** | Polling workers | Each supplier poll is a dispatchable Job on a named queue |
| **Cache-Aside** | Search responses | Check Redis first, fall through to DB, write back on miss |

## 📐 Architecture Flow

```
Scheduler (every N min per supplier, from DB)
    └── dispatches PollSupplierJob → [supplier-polling queue]
            └── SupplierRegistryService resolves Adapter
                    └── SupplierXAdapter::fetchFlights() → FlightDTO[]
                            └── FlightSyncService::upsert()
                                    └── fires FlightDataUpdated event
                                            └── InvalidateFlightCache listener clears Redis

Frontend Request
    └── GET /api/v1/flights?origin=X&destination=Y
            └── FlightSearchService
                    ├── Redis HIT  → return cached FlightResource[]
                    └── Redis MISS → DB query → cache → return FlightResource[]
```

---

*All poll intervals, supplier credentials, cache TTLs, and rate limits are stored in the database or `.env` — nothing is hardcoded. Add a new supplier by inserting a row into `suppliers` and creating one Adapter class.*
